# Caps Lock 输入源与应用焦点

## 问题与修复

苹果简体拼音经 Caps Lock 转发选中后，菜单已勾选拼音，当前应用却继续输出英文；切换到其他应用再返回后恢复中文。build 22 只等待 `TISCopyCurrentKeyboardInputSource` 连续两次返回目标 ID，无法覆盖另一个进程的文本输入上下文未刷新的情况。[同类跨进程问题记录](https://github.com/pqrs-org/Karabiner-Elements/issues/1602#issuecomment-605628367)。

现在只在切入中文输入源时刷新应用焦点：选择前保存前台应用，先确认目标输入源 ID，再短暂激活 QuietDesk 的 1×1 完全透明窗口，等待主运行循环处理输入服务，随后恢复原应用。窗口不接受鼠标，不显示文本，不模拟额外快捷键，不改变系统键盘设置或应用激活策略。原应用本来就是 QuietDesk 时，系统接口作用于本进程，省去这次焦点切换。

取得临时窗口的实际键盘焦点后，按 20ms 间隔等待八轮，再请求恢复原应用。激活与恢复各最多观察 25 轮，必须实际看到原应用重新成为前台；窗口随后关闭，并再次确认输入源 ID 连续两次匹配目标，才回复“远端输入源已确认”。调度繁忙时实际等待可能超过名义间隔；这些观察不等同于已验证真实中文候选词。

整个流程仍位于原有 TCP 消息处理屏障内，后续键盘消息等待焦点恢复。UDP/TCP 视频路径保持原样。切回 ASCII 不创建临时窗口；短按切中英文、长按后松开切大写、大写开启时短按先解除大写等原语义保留。Caps Lock 关闭或旧对端未协商输入动作时，不进入新增流程。

## 失败、取消与兼容

- 前台应用在选择和刷新之间变化，或刷新期间用户切换到其他应用时，停止此次刷新；清理时仅在 QuietDesk 仍占有前台时尝试归还焦点，不把用户选中的其他应用切回去。
- 激活被拒绝、窗口未取得键盘焦点、原应用退出、恢复失败或原应用恢复时输入源被系统改回，均不能回复成功。关闭临时窗口，释放已记录的按键和鼠标状态，提示点击远端输入位置后继续；此前排队的键盘和 Caps Lock 动作不继续注入。鼠标移动不能解除此保护，明确鼠标按下后恢复输入。
- 释放控制、断开、暂停、权限变化仍通过原有 `releaseAll` 使在途确认失效；取消不发送迟到的成功反馈。清理尝试归还仍属于本流程的焦点，但系统已接收的输入源选择及激活请求无法撤销。
- 输入源 ID 不代表密码框允许中文，也不能证明第三方输入法内部的中英文模式。若系统按文稿恢复了其他输入源，当前实现明确报错，不重复切换或发送猜测的系统快捷键。
- 未修改协议、能力协商、配对资料、连接记录、权限检测或监听恢复。复用范围为被控端 `InputSources`、`InputInjector` 及随附检查程序；新增焦点访问边界仅用于本次中文切换和隔离检查。

build 22 的 Caps Lock 监听超时恢复继续保留：只有权限有效且原监听恢复成功才继续工作，清除被打断的手势；用户停用、权限失效或恢复失败仍走停止与提示流程。

## 验证方法与限制

自动检查使用假输入源、假前台应用和假事件投递，覆盖目标 ID 已匹配但焦点未刷新、异步激活与恢复、第三应用抢占、取消、超时、恢复后输入源反转、错误后的按键保护，以及 UDP/TCP 视频下紧接按键的回环顺序。普通键盘、鼠标、滚轮和画布检查继续运行。

独立 bundle ID 的原生合成预览验证真实 AppKit 透明窗口能取得焦点、原测试应用能恢复、临时窗口能关闭；不切换真实本机输入源，不注入按键，不启动生产连接。该检查不等于实际双机拼音验收。

真实两机复测：更新被控端后，在普通文本框中从英文短按 Caps Lock 切入苹果简体拼音，立即输入 `nihao`，应直接出现中文候选词，无需手动换应用。分别检查 UDP/TCP、多个目标应用、快速重复切换、长按大写及释放控制。macOS 14、Intel 实机、多空间/全屏、特殊输入法和本地用户同时切换应用仍需验收。
