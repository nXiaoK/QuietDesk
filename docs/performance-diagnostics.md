# 性能诊断

本次改动增加可开关的阶段计时和日志分析，帮助定位视频卡顿。它不是性能修复，没有改变网络协议、画质选择、帧控制或重连策略，也尚未完成双机卡顿场景的实测验收。

## 收集两端日志

1. 在控制端和共享端的菜单栏 QuietDesk 菜单中都开启「性能诊断」。默认关闭，不持久化；现有连接可以直接开启，不必重连。
2. 保持已经复现问题的画质（本次为 1920 / 30 fps / 8 Mbps），先静止约 15 秒，再持续播放相同视频或动画约 2 分钟。记录动态画面开始时间和卡顿时间；已经确认无鼠标输入也会卡时，不必再重复鼠标对照。静止画面出现 0 fps 是正常节流。
3. 两端分别选择「导出诊断日志…」，保留原始文件并标清控制端、共享端。导出会先收集尚未写出的性能窗口。完成后可关闭「性能诊断」。

菜单或设置操作可能释放控制画面的焦点，需要输入时应重新点入画面。心跳约 5 秒更新一次，几秒钟的观察不足以比较；这次短时复现也能避免 10 分钟无操作导致的自动暂停。

日志只新增枚举指标、消息类型编号、阶段耗时、字节数、计数及匿名本地连接/帧序号。不记录画面、键盘内容、剪贴板内容、设备名称、地址或配对码。构建元数据可包含经过校验的源码提交号。

## 生成报告

在仓库根目录运行，使用系统 Python 3，无第三方依赖：

```sh
python3 scripts/analyze-performance.py viewer.jsonl host.jsonl --output report.md
```

导出的 `.txt` 也可直接作为输入，文件内容是 JSONL。省略 `--output` 时输出到终端；脚本不会覆盖输入日志，也不会连接设备或读取真实凭据。

报告按输入文件、角色、本地启动段、connectionID、指标和消息类型分组。`applicationStarted` 分隔同一日志中的不同应用启动，避免重启后重复使用的本地连接编号混在一起。起始片段缺少启动记录时会明确标注。未知、损坏或不符合类型约束的行会跳过并计数；没有有效样本时显示「缺少诊断数据」，不会当成零耗时。零值只代表该测量记录到零或低于计时精度。

样本数是各窗口 count 的总和；均值按 count 加权，原始窗口均值已取整，因此汇总均值为近似值；最大值取所有窗口的最大值。**P95 只显示「各窗口 P95 上界的最大值」，不能由这些摘要合成全会话 P95。** 时间从微秒换算为毫秒，字节从 B 换算为 KiB（1024 B），计数指标保持 count。

峰值行保留对应的 worstIdentifier 和源文件行号；并列峰值保留一个对应标识。视频和 ACK 的标识是帧序号，ping/pong 标识是探测序号，不是任意指标都拥有帧号。connectionID 只在本地进程的对应连接内有效，双端编号相同不意味着是同一会话。先依据复现时间确认双端对应连接，再人工比较同帧指标；不能混合不同连接，也不能跨端直接相减单调时钟。摘要不会保存每一帧，不能还原完整逐帧轨迹。

## 指标含义与判断边界

| 指标 | 测量边界 |
|---|---|
| sendQueue | 调用发送到该消息开始提交给 Network.framework 的等待；build 16 起包括排在匀速发送视频之后的等待。 |
| sendCompletion | 首段提交给 Network.framework 到最后一段 contentProcessed 回调；匀速发送的视频包含分段间隔。不等于对端收到，也不等于网络交付。 |
| receiveHeaderWait | 请求下一个 4 字节消息头到完整读到消息头；不带消息类型或帧号，包含静止等待、帧间隔和调度，不能直接当作网络时延。 |
| receiveBody | 已读完消息长度后，到消息体读取、解析完成；不包含等待下一帧头的空闲，但包含传输、对端生产及本端调度。 |
| messageHandler | 协议消息交给处理器，到处理器允许继续接收的时间。 |
| roundTrip | 应用心跳往返，包括应用发送/接收排队，不等同于独立 ICMP ping。 |
| tcpSmoothedRTT / tcpMinimumRTT / tcpRTTVariance | Network.framework 传输报告提供的 TCP 平滑 RTT、最小 RTT 和 RTT 变化估计；按 Swift `TimeInterval` 换算为微秒保存。系统底层 RTT 读数可能只有毫秒精度，零也可能低于该精度；RTT 变化估计不解释为统计学上的方差平方单位。 |
| tcpRetransmittedBytes / tcpOutOfOrderBytes | 每次系统传输报告区间内的 TCP 重传发送字节数及接收乱序字节数；不是丢包数量、累计全会话值或速率。无报告不代表零重传。 |
| tcpSentBytes / tcpReceivedBytes / tcpReportDuration | 同一系统传输报告内发送、接收的传输层字节数，以及实际报告区间时长（微秒）；用于结合流量观察重传，字节数不等同于应用视频载荷。 |
| pendingSendBytes | 采样时尚未收到 contentProcessed 回调的发送字节数，包括等待匀速提交的视频；不是 TCP 内核队列的直接读数。 |
| captureAge | 采集回调保存最新画面，到选择该画面编码的等待；不含 ScreenCaptureKit 内部采集/交付耗时，也不统计暂停或重配时有意重放旧画面的等待。 |
| captureInterval | 相邻有效采集回调的间隔；暂停、重配和诊断开关边界不连续累计。它包含供帧及回调调度间隔，不是显示器的刷新间隔。 |
| encodeSubmit | 同步调用 VideoToolbox 提交一帧的耗时，可用于检查采集队列是否在提交时被阻塞；不等于完整编码时间。 |
| encode | 提交编码到应用收到编码结果的时间，包含 VideoToolbox 工作及输出回调中的 AVCC 数据准备，不是纯硬件编码耗时。 |
| encoderDropped | 编码器正常主动丢弃的帧数，每次记录值为 1；看样本数表示次数。失败、旧代或没有有效诊断 token 的帧不会补录。 |
| encodeCallbackQueue | VideoToolbox 输出回调到采集队列实际处理结果的等待。 |
| encodedBytes / keyframeBytes | 视频压缩数据大小，以及其中关键帧的数据大小；不含全部协议和 TLS 开销。 |
| videoAck | 主机收到编码结果回调，到采集队列处理该帧解码确认；包含编码回调排队、发送、接收、解码及确认返回，不是单独的解码耗时。 |
| decodeQueue | 视频交给解码器到解码队列开始处理的等待。 |
| decodePrepare | 准备 sample、格式和解码 session 到提交 DecodeFrame 前；包括重建时等待旧 session 完成。 |
| decode | DecodeFrame 提交到异步解码结果回调。 |
| decodeToDisplay | 最新保留的解码结果放入容器到显示层入队完成；包含主线程调度和显示层就绪等待。连续被新帧替换会缩短该值，不能用它代表整个界面停顿时长。 |
| displayEnqueue | 准备显示用格式/sample 并调用显示层 enqueue 的耗时，不等于真正上屏或端到端可见延迟。 |
| captureReplaced / displayReplaced | 旧的待编码/待显示帧被更新帧替换的次数；为有界最新帧策略的观测，不直接代表网络丢包。 |
| videoOutstanding | 编码中及等待解码确认的帧数量采样。 |
| encoderHardware / decoderHardware | 查询成功时记录 1（硬件）或 0（软件）；查询失败或尚未查询没有样本，nil/缺少不代表软件模式。 |

先比较动态画面期间 video 的 receiveBody、sendQueue、sendCompletion、pendingSendBytes 与 roundTrip 是否同时升高；再比较 encode、encodeCallbackQueue、decodePrepare、decode、decodeToDisplay 是否升高。它们能缩小排查范围，不能单凭一个峰值确认网络、编码器或 UI 是根因。阶段可能重叠，不应直接相加成端到端耗时。

高帧率下最多允许两帧正在编码，因此 `encode` 包含等待前帧的时间；自适应使用的编码处理间隔会排除这部分等待，二者含义不同。原分辨率与缩小分辨率的对照及本机实验边界见[高帧率说明](high-frame-rate.md)。

TCP 指标可帮助区分应用有序消息排队与底层 TCP 等待。开启性能诊断后，已就绪的连接才开始系统传输报告，沿用 Peer 约 5 秒的定时器收集；每次收集回调完成后开始下一报告，区间之间可能有小段空隙，与日志聚合窗口不保证完全对齐。每项每报告记录一次，表中样本数和 P95 针对报告读数，不是逐包 RTT 分布；字节指标的均值也不能当带宽。系统聚合报告对字节数跨路径求和，不可求和的 RTT 使用主路径，本程序不记录接口、路径地址或报告描述。无有效路径的报告不生成这些指标。

`tcpReportDuration` 记录实际系统报告区间，区别于性能摘要的 `windowMilliseconds` 日志聚合时长。发送、接收与重传字节应结合对应报告时长判断；摘要按指标独立聚合，不能把窗口均值直接解释为吞吐，也不能从窗口峰值推导同一时刻的重传比例。

## 开销和清理

启用后以约 5 秒为窗口，用固定桶直方图聚合；不为每帧写一条日志。日志继续受原有待写项、文件大小和保留数量限制。导出、关闭或断开时可能产生短于 5 秒的收尾窗口；定时器调度也可能使实际窗口稍长。

关闭诊断会使旧计时 token 失效，关闭/清理会话会清理计时状态，迟到回调不应混入下一次启用或下一条连接。诊断本身仍有计时、加锁和日志写入开销，测试结果应结合未启用时的实际表现判断。

默认关闭时不创建系统传输报告。开关通知在 Peer 队列处理；关闭时释放未收集报告并使在途收集失效，断开时也移除通知。旧报告通过诊断代次和本地收集标识双重校验，关闭后或重新开启后的迟到回调不会记入新窗口。协议、TCP 参数、心跳调度与界面延迟显示均不因这些指标改变。

运行报告脚本的检查：

```sh
python3 -m unittest discover -s scripts/tests -p test_performance_report.py -v
```

构建脚本增加可选 `QUIETDESK_BUILD_DIR` 和 `QUIETDESK_DIST_DIR`，未设置时仍使用原有 `.build` 和 `dist`。工作树干净时将真实 Git HEAD 写入可选构建元数据；有未提交改动或没有 Git 元数据时留空，不把未提交代码错误标成某个完整提交。打包仍只包含 Git 跟踪的源码，不包含构建缓存、日志和私有签名配置。

本次验证：核心检查 130 项、视频流水线 12 项、合成视频及计时 8 项、日志 11 项、Python 版本与报告 17 项通过。合成 VideoToolbox 和回环 TLS 检查因沙箱限制在允许系统视频服务/本机监听的环境运行，没有录屏或访问真实剪贴板、钥匙串。双架构 Release 编译、Universal 合并、最低 macOS 14.0 和 ad-hoc 签名验证通过；未启动安装的应用。

## build 15：局域网传输对照

build 14 的 ACK stretching 选项启用后，局域网仍出现秒级视频发送和完整消息接收等待。用户确认同样的原分辨率 / 60 fps / 100 Mbps 下外网映射反而流畅；此前 8 Mbps 也曾复现，因此不将自动画质作为充分解释。按用户要求，build 15 保留自动升档、历史偏好及手动选择，仅补充上述系统 TCP 报告。

复测时在两端开启性能诊断，以相同动态内容和相同画质，分别通过内网地址与外网映射地址运行约一分钟并导出日志。记录外网测试时控制端是否仍在同一局域网，或已换到其他网络；本机没有活动连接，未取得此轮真实路径的 TCP 报告。发送重传应看共享端，接收乱序应看控制端，再与应用视频等待对照。不要根据乱序字节比例推断丢包率，也不要仅凭心跳降低声称画面卡顿已消除。

复用范围为 Peer 的可选诊断对象、采集/解码/显示/日志共用的 PerformanceDiagnostics 及离线报告脚本。新增 token 参数默认不传，原数值记录行为保留；系统报告仅在开启时创建，无有效路径或数值时省略对应数据，断开不会等待报告返回。TLS/Wire 格式、网络参数、画质和失败/取消语义不变，无数据迁移。旧版二进制混连及真实链路上的诊断开销仍未验证。

针对性检查：核心 136 项、视频流水线 12 项、视频样本 8 项、会话数据 6 项、日志 11 项以及 Python 18 项通过；包括实际本机 TLS 报告、开关生命周期、旧 token/其他 recorder 隔离和单位校验。运行使用合成视频、回环连接及临时数据，未录屏或操作真实剪贴板、钥匙串、权限或生产连接。这些检查不替代双机 LAN/WAN 对照，尚未确定性控制系统旧报告恰在重启诊断后的回调时机。
