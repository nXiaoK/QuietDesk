# 中继协议与原生转发

## 加密层和通道

```mermaid
flowchart LR
    V[控制 Mac 的桌面 TLS/DTLS] --> VB[私有回环转发桥]
    VB -->|服务 TLS / 带 HMAC 的 UDP 密文| R[Linux 节点]
    R -->|服务 TLS / 带 HMAC 的 UDP 密文| HB[被控 Mac 的私有回环转发桥]
    HB --> H[既有桌面 TLS/DTLS 监听器]
```

节点仅终止外层服务 TLS。内层 TCP 保留原 Mac 配对 PSK 与 ALPN；UDP 保留媒体协商产生的独立 DTLS 密钥。每个控制、视频、bulk TCP 连接分别建立出站隧道，避免将大文件复用到单一控制队列。内层流量继续由现有计量器记账；外层服务与节点转发开销不伪装成应用载荷。

客户端的回环服务只绑定 `127.0.0.1` 随机端口。被控端登记对象记录自己创建的本地 TCP/UDP 源端口，用于标注真实中继路径和抑制回环 TCP 的诊断报告；它不代替桌面认证。用户配置的节点地址决定出站目标，服务返回的私有 `udpPort` 不改变公网端口。

## 服务协议 v1

服务连接首先进行证书验证的 TLS。消息为 4 字节网络序 JSON 长度，加不超过 8192 字节的 JSON，包含 `version: 1` 和 `op`；二进制字段使用 Codable/JSON 的 Base64。

| 操作 | 约束和结果 |
| --- | --- |
| `register` | 接入密钥、设备 UUID、独立 owner 密钥；首次持久化 owner 的 SHA-256 摘要，成功返回 `registered` 和本次在线令牌 |
| `connect` | 鉴权并查找在线设备；向登记连接发送 `incoming` 与随机 circuit ID |
| `accept` | 被控端另建出站 TLS，提交设备、当前登记令牌和单次 circuit ID；双方收到 `ready` 后连接永久变为原始双向密文字节流 |
| `datagram` | 控制端申请 UDP lease；登记连接收到 `incomingDatagram` 与 host 角色凭据；host 的已认证 UDP 端点就绪后返回 `datagramReady` 与 viewer 角色凭据 |
| `ping` / `pong` | 登记与 UDP lease 每 15 秒保活；失联按期限回收 |
| `datagramClosed` / `error` | 明确退役路由或返回有限的错误代码；不返回原始业务或密钥内容 |

节点默认服务握手 5 秒、空闲 45 秒、待接通隧道 10 秒；客户端服务 TLS 建立期限 10 秒。资源限制是套接字/缓存/持久登记表的技术边界，不增加产品用户数或流量套餐。登记断开使关联隧道和 UDP lease 失效。设备摘要在节点重启后保留，在线令牌和路由不持久化；损坏或未知版本的状态文件阻止启动并保留原文件。

## UDP 封装

封包依次包含：4 字节 `QDR1`、1 字节 side、1 字节方向、8 字节递增序号、16 字节 lease ID、2 字节载荷长度、最多 1152 字节内层 DTLS 记录、32 字节 HMAC-SHA256；固定开销 64 字节。整数使用网络序。

side 区分 viewer/host；方向区分向节点与向端点，角色密钥独立。接收方先验证尺寸、用途、HMAC 和 64 个计数的重放窗口，再更新 NAT 端点；计数不允许 0、重复或回绕。节点转发时重新封装外层方向和计数，不修改内层记录。回环代理有有界待发送队列和背压，每个 UDP 数据报保持边界。

## 中继打洞（可选能力）

`register`（被控端）与 `datagram`（控制端）可附带可选的 `assist: true`。节点只在双方都声明时，才在 `incomingDatagram` 和 `datagramReady` 中回传 `assist: true`；未协商时报文与原来逐字节相同，旧节点、旧客户端不受影响。版本号仍为 1。

| 操作 | 方向 | 约束 |
| --- | --- | --- |
| `assist` | 两端 → 节点 | 仅在已协商的租约上发送，带 `datagramID` 和最多 4 个本机 `host` 候选（IP 字面量与端口）。表示该路由的媒体 DTLS 已通过桌面认证；地址变化时可重发 |
| `peerCandidates` | 节点 → 两端 | 双方都发送 `assist` 后才下发：对方的节点观察地址（`srflx`）加对方自报的 `host` 候选，最多 8 个。观察地址变化时更新，每个租约每秒最多一次 |

节点和客户端都拒绝主机名、带作用域、未指定、组播、广播和链路本地地址，自报候选也不能是回环地址；只有节点本身在回环地址时，客户端才接受回环的观察地址。节点不知道打洞是否成功，也不参与直连封包。

直连封包 `QDP1` 布局与 `QDR1` 相同，固定开销 64 字节：4 字节魔数、1 字节发送方、1 字节类型（数据 / 探测 / 探测回复 / 提名 / 提名确认 / 释放 / 开始尝试；最高位表示在中继数据报内传输）、8 字节序号、16 字节租约 ID、2 字节长度、载荷、32 字节 HMAC-SHA256。密钥为 `HKDF-SHA256(媒体 datagramKey, salt=媒体会话 ID, info="QuietDesk relay peer path v1")`，再以租约 ID 为盐分别派生两个方向的密钥。`datagramKey` 只在已配对的控制 TLS 内传递，节点拿不到，所以无法伪造直连封包。直连与中继内的封包各有独立序号和 64 计数重放窗口。

数据封包载荷就是原样的内层 DTLS 记录。DTLS 记录首字节为 20–25，不会与 `Q` 冲突，所以 `QDP1` 也可以放进中继数据报，用来测量中继路径往返和通知对端。

## 桌面媒体扩展

`Hello` 新增可选 `relayTransportV1` 与 `relayDeviceID`。媒体 `request/offer` 新增可选 `relayRouting`，双方确认后才启用新恢复语义。`recover.mediaFailure` 只在协商成功且发送方实际缺少重组确认时发送；旧端继续使用原消息。节点 URL 不经 Hello 下发，也不信任对端提供的任意服务器。

默认 Core 工厂关闭混合恢复；DeskModel 只为明确配置的连接启用，并核对认证后的 Hello 设备标识。直连可靠视频真实交付失败后可准备配置节点的 UDP 桥；编码准备失败、已重组帧的解码超时、静止或暂停不会触发中继试用。首个不同路径可试用一次，此后沿用既有退避。TCP-only 不建立 UDP 候选。

媒体仍使用原 `prepare/ready/decodedReady/commit/committed` 事务和流代次。真实 IDR 解码并完成双方提交后才更新展示路径；旧画面保持到提交。新 DTLS 握手只在协商此能力后允许有界待认证候选，认证成功前保留旧连接，旧连接的关闭回调不能清除新连接。

重复可靠交付失败通过有界回调请求全中继重连或明确失败。只切换视频时保持同一个控制 Peer，重建控制时沿用释放输入、重新认证和传输取消语义；用户取消、睡眠、暂停和关闭自动重连仍受原会话身份与状态保护。
