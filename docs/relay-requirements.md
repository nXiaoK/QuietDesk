# QuietDesk 中继功能需求 v1

状态：用户已批准第 2 节的首期范围。技术方案采用 Go 标准库单节点服务与原生 Swift 转发桥；使用方法见 [中继使用说明](relay.md)，部署见 [节点指南](../relay/README.md)。性能数字仍是待实测的目标，不能据此认定公网体验已验收。

## 1. 目标与现状

中继提供一条可替代直连的网络路径，重点解决公网地址不可达、无法配置端口映射，以及部分直连路径质量较差的问题。稳定性取决于两端网络、中继节点位置、带宽和服务健康，不能承诺所有场景都比直连更快、更稳定。

实施前的直连方式先建立配对认证的 TCP 控制连接，再协商直连 UDP 视频；UDP 不可用时使用独立 TCP 视频或控制连接中的兼容传输。首期保留这些协议，增加外层服务 TLS 隧道和 UDP 密文转发。键鼠、设置与会话控制始终可靠传输，文件和自动剪贴板继续优先走独立 TCP 数据连接；首期没有通用 NAT 打洞。

**关键范围：只增加 UDP 视频中继，仍然需要先连通原 TCP 控制连接，不能解决没有端口映射时完全无法连接的问题。**

| 方案 | 能解决的问题 | 仍有的限制 | 评审建议 |
| --- | --- | --- | --- |
| 仅媒体中继 | 已连通会话可尝试另一条视频路径 | 控制连接仍需直连，不能独立解决免端口映射连接 | 可作为缩小首期范围的备选 |
| 全会话中继 | 控制、视频、文件均能通过双方主动出站连接建立，支持无入站映射场景 | 需要设备登记、会话寻址、可靠通道和服务器运维 | 推荐作为完整产品目标 |

## 2. 首期建议

建议首期支持：**自托管单节点、全会话中继、已知地址直连优先、UDP 视频优先、可靠传输兜底、保持端到端配对认证和加密。**

| 纳入首期的建议范围 | 后续范围 |
| --- | --- |
| 用户配置自有中继服务；两台 Mac 主动连接同一服务 | 官方公共中继、多地区节点与自动选区 |
| 已配置直连地址时尝试直连，必要时使用中继 | STUN/ICE 通用打洞及复杂 P2P 候选发现 |
| 通过设备标识连接被控端；旧 IP/端口连接继续保留 | 云账号、设备目录、计费、套餐与管理后台 |
| 中继承载可靠控制、视频与既有文件/剪贴板功能 | 音频、FEC、文件断点续传等新增业务能力 |
| 中继 UDP 视频与可靠视频兜底；沿用已有画质上限 | 多节点集群、跨节点迁移和高可用服务承诺 |

客户端继续使用原生 SwiftUI/AppKit、macOS 14+ 与 Universal 构建。服务端采用 Go 1.25+ 标准库，生成 Linux amd64/arm64 独立程序；使用专用 v1 协议，不兼容标准 TURN 客户端，也不在 Mac 中嵌入 Go 运行时。

TURN 可提供转发能力，但不自动提供设备在线登记、配对、信令和路径决策，这些产品能力仍需设计。

## 3. 用户场景与流程

### 3.1 无端口映射连接

1. 部署者准备中继服务。两端配置服务地址；服务接入鉴权的发放方式在技术方案中确定，首期不新增云账号体系。
2. 被控端明确启用中继并开启共享，主动连接服务；界面展示设备标识、中继连接状态和真实共享/权限状态。
3. 控制端选择“通过中继连接”，填写目标设备标识并使用原有配对码认证。
4. 服务负责找到目标和转发密文。只有两台 Mac 完成配对认证后，才能开始画面、控制或数据传输。
5. 设备离线、未开启共享、鉴权失败和版本不支持时，显示实际原因；不得伪装成一直“正在恢复画面”。

```mermaid
flowchart LR
    V[控制 Mac] <-->|已知地址可达时直连| H[被控 Mac]
    V <-->|主动出站连接／密文| R[自托管中继服务]
    H <-->|主动出站连接／密文| R
```

此处“免端口映射”指两台 Mac 无需开放入站映射；中继服务器自身仍需有双方可达的服务端口。

### 3.2 已有公网映射的连接

用户原有地址、端口、配对码和画质偏好继续可用。主动启用中继后，已有直连地址可作为候选；直连不可用或视频持续恶化时，系统可试用中继。

首期仅设备标识、没有已知直连地址的连接直接使用中继，不宣称已具备通用 P2P 打洞。中继服务故障不能阻断原本可独立工作的 IP/端口直连。

### 3.3 可选择的连接策略

| 策略 | 行为 |
| --- | --- |
| 仅直连 | 保持现有行为，不联系中继服务；旧连接记录缺少新配置时沿用此行为 |
| 自动 | 用户启用后，在已知可达的直连路径和已配置中继之间选择；优先保留健康的直连 |
| 仅中继 | 不尝试目标 Mac 的直连路径，便于特定网络使用与问题定位 |

原有“仅使用 TCP”选择继续生效：启用时同时跳过 UDP 直连和 UDP 中继视频尝试，不能因开启中继而重置已有选择。

## 4. 功能需求

### R1：中继配置与设备寻址

- 启用中继是明确的用户选择，默认不连接公共服务、不上传设备信息。
- 可配置服务地址，保存和编辑时验证格式；部署端口可配置。TCP 443 可作为部署候选，但不承诺所有企业代理均可通过。
- 被控端具备持久、可展示的设备标识；标识只用于寻址，不能作为控制凭据。是否复用现有本地设备标识需在设计阶段核对，不能把流量统计标识直接视为身份认证。
- 保留现有单控制会话等业务行为，不新增人数、流量配额、角色或审批流程。
- 服务“已连接/在线”与“共享已开启”“屏幕录制可用”“允许控制”分别显示，均绑定真实状态。

### R2：会话与数据通道

- 即使目标 Mac 没有入站映射，也能经中继完成配对认证、观看和既有键鼠控制。
- 键鼠、设置、权限状态、暂停/恢复和独立光标保持可靠、有序传输；切换路径不得重复注入输入。
- 视频优先试用中继 UDP；UDP 被阻断或媒体不可用时，仍能通过可靠中继路径传输画面。
- 文件、文字和图片剪贴板按既有能力与开关工作。文件仍逐次确认，失败仍取消并清理半成品，不增加隐式接收或虚假的断点续传。
- 大文件与视频不能无限占用控制消息发送机会；通道队列、缓存和发送背压需有界。

### R3：路径选择与恢复

- 路径选择依据真实媒体可用性与持续观测，不能仅凭 ping 成功、低 RTT 或一次丢包判定更优路径。
- 健康的直连 TCP 可以继续使用，不因配置了 UDP 中继就无条件切换。
- 候选路径在真实关键帧解码并提交后才显示为已生效；媒体切换期间保留旧画面，沿用现有参考链隔离和旧回调失效机制。
- 切换失败保留当前可用路径；恢复探测要有冷却、退避和稳定观察，不能不断往返切换。
- 保留交付与解码预算的区分，不把中继视频再次套入过短的统一超时；静止画面和空闲暂停不当作故障。
- 仅视频路径切换时保持控制会话、画布焦点和输入所有权。控制连接确需重建时，按现有重连语义释放输入、重新认证并处理未完成传输，首期不承诺控制连接无缝迁移。
- 网络变化、节点断开和系统唤醒后重新验证；重连和候选成功的迟到回调不得覆盖用户取消。

### R4：安全与隐私

- **中继服务不能获得 Mac 配对码、端到端会话密钥，或解密画面、按键、剪贴板、文件内容。**原有端到端认证必须覆盖中继路径，不能改为仅信任服务端。
- 两端连接中继服务时验证服务身份；不得跳过证书校验或失败后改用明文。
- 服务接入鉴权与 Mac 配对认证分离：能使用中继不等于能控制某台 Mac。不得形成未鉴权的开放转发服务。
- 登记、路由绑定和会话令牌需校验身份、用途与有效期，防止串线、冒充、重放和越权转发；不得信任对端或服务返回的任意字段。
- 服务可以观察连接地址、时间和流量规模，文案不能声称“中继完全看不到任何信息”。不保存业务明文，日志最小化并明确保留与清理策略。
- 客户端机密存储沿用现有已说明的本地安全边界，不擅自新增钥匙串访问。服务端机密不写入源码、日志、源码包或 GitHub。
- 不新增 macOS 权限；权限刷新、控制状态订阅、Caps Lock 监听恢复与输入法确认顺序保持原行为。

### R5：状态、诊断与统计

- 分别展示实际控制路径与视频路径，支持“直连控制 + 中继 UDP 视频”这类混合状态。
- 视频状态能区分直连 UDP、直连 TCP、中继 UDP、中继 TCP，以及尚在探测/恢复的状态；兼容通道须准确标注。
- 控制 RTT、中继/媒体探测 RTT、解码帧率和实际画质分别解释，不能把心跳当作端到端可见延迟。未测量的数据不显示为零。
- 诊断记录路径变化、失败阶段、恢复次数和有测量依据的字节/时延，不能记录密钥或业务内容。
- 原应用流量统计继续按实际发送/接收记账；中继节点带宽与云账单另行解释，不与客户端应用层流量混为一谈。

### R6：节点部署与运行

- 首期建议支持一台双方可达的 Linux 服务器，提供部署、启动、停止、升级、回退、证书和排障说明；具体服务组件待选型。
- 节点有真实健康状态和必要运维指标。故障时客户端应给出明确原因并尝试其他可用路径，不无限等待。
- 握手、登记、会话、缓存与队列有技术资源边界，过期资源及时回收；这些边界不得擅自变成用户人数或业务流量配额。
- 节点不负责解码、转码或修改画面，客户端保留既有画质上限与自动降载规则。

## 5. 兼容与已有数据

- 旧客户端与旧服务缺少能力时，沿用原有直连方式；用户指定仅中继而对端不支持时明确报错，不静默假装已经中继。
- 新网络能力显式协商，字段可选，缺失时保留旧行为；不得在未协商前发送旧端不认识的消息。
- 保存的连接、配对码、画质、权限开关与历史流量保留。设备标识类连接与 IP/端口类连接的关联方式需明确，不能简单覆盖原记录或把新路径当作新的控制授权。
- 服务端持久化哪些登记数据、如何兼容升级与清理离线设备，在数据设计阶段明确；不能预设没有需保留的存量数据。

## 6. 验收场景

| 场景 | 期望结果 |
| --- | --- |
| 未配置中继、旧记录、旧对端 | 原直连和失败/取消语义保持可用 |
| 两台 Mac 均无入站映射，但能访问节点 | 经中继完成配对、首帧、输入和既有数据传输 |
| UDP 完全被阻断，可靠中继可达 | 能经可靠路径观看和操作，状态准确 |
| 直连良好，中继更慢或不可用 | 继续直连；节点故障不拖垮既有直连 |
| TCP 控制直连，视频改用中继 | 输入不重复、焦点不丢失，界面分别展示路径 |
| 候选丢包、解码失败、显示层忙碌 | 保留旧图像；失败不提交；不周期清屏或无限恢复 |
| 实际网络切换、中继重启、睡眠/唤醒 | 有界恢复或明确失败；释放输入与本机效果保持原语义 |
| 静止画面、空闲暂停、恢复后立即输入 | 不误判失联；等待新画面与输入保护继续生效 |
| 错误配对码、无权接入、伪造标识/令牌 | 拒绝访问，不泄露业务内容或接错设备 |
| 传文件时操作、取消、断线 | 控制可响应；确认规则保留；半成品按既有流程清理 |
| Caps Lock 后立即输入中文 | 在直连、混合和全中继路径均维持确认与焦点恢复顺序 |

测试矩阵应覆盖局域网、公网映射、无入站映射、UDP 阻断、丢包/乱序/抖动、节点带宽不足，以及 macOS 14+、Apple 芯片与 Intel。合成回环不能替代真实双机验收。

**性能目标提案，待评审后固定：**在双端到节点 RTT 各不超过 80 ms、上下行有余量、无人工丢包，使用 1920 / 30 fps / 8 Mbps 的受控基准下，首帧 P95 不超过 5 秒、仅视频路径切换 P95 不超过 3 秒。实际可见首帧和切换要由可见画面测量，不能用解码回调或 RTT 代替。持续运行与反复故障测试需验证没有无休止恢复、路径抖动、资源持续增长或重复输入；弱网下允许降载，不承诺固定 60 fps。

## 7. 部署成本与技术预研

以**实际平均**单向视频载荷 8 Mbps 为例，约为 3.6 GB/小时；节点转发这一载荷约产生 3.6 GB 入站和 3.6 GB 出站，另有控制、协议、文件和补传开销。云服务按出站还是双向计费需看供应商，不能直接把客户端统计当账单。

实施前先验证原生客户端通过转发通道保持端到端 TLS/DTLS、可靠控制与 UDP 边界的可行性，再确定服务组件和协议。服务端认证、设备寻址、端到端认证和媒体路径协调应分清职责，不能把引入某个 TURN 服务等同于整项功能已经完成。

## 8. 已确认的产品选择

1. 首期采用全会话中继与自托管单节点，两端主动出站访问同一节点。
2. 新增设备标识入口，保留现有 IP/端口连接；默认仅直连，启用后才联系节点。
3. 节点接入码由部署者安全分发，不新增账号、角色、收费、人数或流量配额。
4. 同时覆盖已有公网映射的混合视频恢复，以及没有 Mac 入站映射的全中继连接。
5. 真实双机、公网、Linux 部署和可见延迟仍需按第 6 节测试矩阵验收；合成回环与交叉编译不能替代这些结果。
