## 复用、兼容与失败路径

复用范围为应用及随附 Core / AppChecks。检索并检查了 Peer、Wire/ByteReader、VideoEncoder/VideoSamples/LatestFrameMailbox、ScreenStreamer、ClipboardTransfer/ClipboardSync、文件提示倒计时及 DeskModel 的调用链。

- Wire 版本和消息编号保留。ClipboardPreference/Begin 的窗口字段可选，缺字段保持旧分块行为；文件确认门槛保留，确认前无文件载荷和接收子目录。
- Peer 的有序完成处理器按需启用，原 onMessage 路径保留；继续回调只能恢复一次，旧回调或关闭后的回调不能恢复读取。显示邮箱不传序号的既有调用保持原覆盖行为。
- Core 的旧 onApply 回调保留；应用启用可选许可后，后台校验成功且许可仍有效才写入系统剪贴板。新复制、远端替换、取消和停止使旧许可失效。发送准备票据只供后台转换使用，普通 send 仍沿用原调用方式。
- 接收容量不足或写入失败只取消本次剪贴板传输，取消/断线不发布半成品。磁盘容量是开始前的检查，不能保证随后空间不被其他进程占用。
- 不清理用户已经接收的文件；无法证明失活的旧版临时目录保留。NSData 桥接可能复制，但没有跨 withUnsafeBytes 生命周期持有临时指针。
- 连接记录、钥匙串结构、默认画质、快捷键和权限恢复逻辑保留。改动没有给系统授权，也未改变签名身份或安装生产应用。

## 问题 5：前向保密的可行性核查（尚未解决）

现有连接继续使用 Network.framework 的 TLS 1.2 / `TLS_PSK_WITH_AES_128_GCM_SHA256`，保留旧端互连。该套件不提供前向保密；本轮没有把放开 TLS 版本范围当作安全修复，也没有修改配对码或钥匙串数据。

本机使用独立临时程序，只在 `127.0.0.1` 建立连接，并使用合成的 32 字节 PSK 与现有 `quietdesk-v1` identity。关闭 TLS tickets 和会话恢复，比较相同配置的两条路径：

- TLS 1.2 对照组握手成功；系统 metadata 显示协议 `0x0303`、套件 `0x00A8`，即现有纯 PSK 套件。
- 服务端允许 TLS 1.2–1.3，客户端要求 TLS 1.3，并添加 `TLS_AES_128_GCM_SHA256` 时，客户端进入 `waiting(-9858: handshake failed)`，服务端返回 `-9816`。该路径未能建立 external PSK 会话，不能据此启用 TLS 1.3。
- 当前公开 `sec_protocol_options_*` 接口可添加 external PSK、协议版本和套件，但未提供显式强制 `psk_dhe_ke` 的控制。仅观察 TLS 1.3 版本或 AEAD 套件也不足以证明使用了临时 DH。

这些结果只反映本机 macOS / Network.framework 实现，不证明所有系统版本都不支持该模式。要解决此问题，需要单独完成可验证的 TLS DHE-PSK 路径，或设计并审计按能力协商的应用层临时密钥协议；同时验证旧版降级提示、认证交换、密钥确认、方向隔离、重放防护与密钥销毁。当前仍需把配对码视为长期秘密，经可信渠道传递，泄露后停止共享并重新生成。
