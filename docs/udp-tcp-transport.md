# UDP/TCP 自动媒体传输

[使用指南](usage.md) · [安全说明](security.md) · [开发与检查](development.md)

本文对应当前源码中的新媒体模式。两端通过可选的 `mediaTransportV1` 能力启用，继续使用原生 SwiftUI/AppKit、ScreenCaptureKit、VideoToolbox 和 Network.framework，最低系统目标为 macOS 14，构建目标包含 Apple 芯片与 Intel。支持的系统与架构不代表已完成对应实机性能验收。

## 一条会话如何传输

TCP 配对认证的控制连接先建立，并在整个会话中保留。UDP 负责可及时恢复的视频数据，键鼠、设置、暂停与恢复协商始终使用可靠 TCP。

| 组成 | 当前实现 |
| --- | --- |
| 认证与控制 | 原有配对码认证的 TLS TCP；持续承载键鼠、控制消息和心跳 |
| 首选视频 | 会话密钥认证的 DTLS UDP，应用层分片、有界重组、有限补传和参考链恢复 |
| TCP 视频 | 通过同一监听端口建立独立 TLS TCP 连接，绑定媒体角色与当前控制会话 |
| 文件与自动剪贴板数据 | 优先通过独立 TLS TCP bulk 连接传输；辅助通道不可用时回到控制连接 |
| 新版兜底 | 独立视频 TCP 不可用时，在控制 TCP 内发送新媒体封装，界面显示“TCP 兼容模式” |
| 旧版对端 | 缺少媒体能力时使用原来的视频与 ACK 消息，不发送未协商的新媒体消息 |

“仅使用 TCP”关闭本次新连接的 UDP 尝试，仍可使用独立视频与 bulk 连接。它不强制改回旧版视频协议。

视频为有损 H.264 / 4:2:0，两端都有 HEVC 硬件编解码时改用 HEVC（见[高帧率说明](high-frame-rate.md)）。客户端使用 VideoToolbox 解码、最新帧容器和 `AVSampleBufferDisplayLayer` 显示；新候选路径有独立解码器，解码完成可以先返回确认，提交前不替换正在显示的画面。

## 认证与协议边界

TCP 使用系统 TLS 1.2 / PSK / AES-128-GCM；UDP 使用系统 DTLS 1.2 / PSK / AES-128-GCM。主机通过已认证的控制连接交换本次会话随机生成的媒体 PSK 和绑定令牌。临时媒体密钥独立于持久化配对码，不写入凭据文件或诊断日志；它不提供额外的前向保密，因为密钥交换仍依赖原来的 PSK TCP 会话。

独立 TCP 连接通过 ALPN 区分控制、视频和 bulk，再使用有时限的令牌绑定到当前控制会话。握手、待绑定连接、接收队列、分片与重传缓存均有限，角色不符或未绑定的连接不能直接注入媒体反馈。

媒体封装携带会话 ID、传输代次、编码代次、帧 ID 和关键帧标记。接收端按编码格式验证 H.264/HEVC 内容与关键帧标记，检查分片数量、范围、重复内容及总大小。旧会话、旧代次、过期解码结果与重复确认不能提交新画面或释放新帧的信用。控制端可在媒体请求中声明接收窗口（当前为 6 帧）。共享端在低于 60 fps 时最多发送 4 个在途帧，从 60 fps 起最多 6 帧，且不超过对端声明的窗口。缺少该字段时沿用 3 帧上限。发送与重组缓存另有字节数限制。

加密 UDP 媒体连接（直连 DTLS、发往中继节点的 UDP 以及打洞直连的套接字）标记为系统的“交互式视频”服务类别，Wi‑Fi 会按视频接入类别而不是尽力而为来调度这些包；控制、独立视频 TCP 和 bulk 连接保持默认类别，端口映射保持后台类别。这只是给系统和无线链路的调度提示，不改变协议字节，路由器是否据此优先转发取决于设备；尚未在真实 Wi‑Fi 上做过对照测量。

配对码的保存方式、文件接收确认、系统权限和既有快捷键不因传输模式改变。具体安全边界见 [安全说明](security.md)。

## 建连、切换和恢复

1. 双方先完成 TCP 配对认证与媒体能力协商。主机提供会话材料；客户端尝试辅助 TCP 连接及 UDP 双向探测。
2. 控制端协调路径切换，双方通过可靠控制消息确认新的会话代次和目标路径。
3. 共享端暂停原参考链，重建编码器并发送带 SPS/PPS 的真实 IDR。接收端在候选解码器中解码，提交确认后才替换显示源，并恢复连续出帧。
4. 失败或取消会失效对应候选、旧缓存和迟到回调。旧画面可保留到新关键帧就绪，传输状态在实际提交后更新；视频切换不调用画布的控制释放流程。

同路径快速恢复：恢复发生在当前正在使用的视频路径上时（最常见的情况：一帧补不回来），路径本身不需要再证明。双方在媒体请求/回复中协商可选的 `fastRecovery` 后，这类事务改用较短的交换：

- 控制端发出 `prepare` 时就建立新代次的重组器，并在 UDP 上再发一份同样的请求（约每 50 ms 重复，直到共享端回应），控制连接上丢一个 TCP 段不再拖住恢复。
- 共享端准备好后照常在控制连接上回 `ready`（此前发出的光标绑定等消息因此先到），但不等控制端的 `ready` 回复就出关键帧。UDP 上的关键帧要等“本次恢复开始之后发出的那次保活探测”得到回应：这个探测排在旧视频流已发出的所有数据包后面穿过链路，收到回应说明链路已恢复、途中队列里也不再积着旧数据包，关键帧不会被发进仍然中断或仍然堵着的链路。探测在收到请求时立即发出并约每 50 ms 重发，与共享端准备编码器同时进行。
- 控制端收到共享端的 `ready` 后才解码这帧关键帧，解码成功即提交并回 `committed`；共享端以控制端的解码反馈（UDP）或 `committed`（TCP）中先到的一个为准恢复连续出帧。

相比完整事务少两次控制连接往返，仍然更换编码代次、发送真实 IDR，旧画面同样保留到新关键帧提交。更换视频路径、首次建流、任一端未协商该能力时沿用上面的完整流程。

同一光标模式下的媒体恢复不移除显示层已保留的图像。候选解码失败、取消或显示层暂时忙碌时，旧图像继续保留到可入队的新画面就绪；新关键帧提交仍会失效旧解码回调。真正切换视频内光标与独立光标时仍清理旧图像以防重影，主动断开或重置会话也仍清屏。

前向纠错的覆盖范围：

- 多片帧按每组最多 10 片附加 1–3 个 Reed-Solomon 校验片。控制端在媒体请求中用可选的 `fecFragmentLimit` 声明自己接受校验片的最大帧（当前 4096 片，约 4 MB，覆盖原分辨率关键帧）；旧控制端不声明，共享端对它仍只保护 256 片以内的帧，不发送它会拒收的校验片。
- 发送队列里还有上一帧的积压时（滚动、播放视频时的大帧），近 8 秒内出现过补传请求且积压不超过约 100 ms 的发送量，仍附加比无积压时少一档的校验片；链路没有丢包迹象或积压更长时不附加，避免加重排队。
- 只有一片的小帧（打字、光标闪烁）没有可保护的分组：近 8 秒内出现过补传请求时，共享端约 4 ms 后把这一片原样再发一次，旧控制端按重复分片忽略多余的一份，不需要协商。
- 帧的送达截止时间计入随帧发送的校验片和排在它前面的积压，自身匀速发送占用的时间不消耗补传窗口。

尾帧探测：控制端只能请求“已收到内容之前”的缺片。一帧整帧丢失且后面没有新帧时（例如画面静止前的最后一个小帧），控制端不知道它存在，以前只能等共享端截止时间到期后更换整条参考链并重发关键帧。现在共享端只对“最新的一帧”做探测：它的原始分片全部发出后，约 1.5 倍往返时间加 20 ms（不少于 30 ms）内既没有更新的帧发出，也没有收到控制端关于这一帧的任何反馈（重组完成或补传请求），就把该帧最后一片再发一次：单片帧由此直接补齐，多片帧则让控制端看到缺口并照常请求其余分片。更早的帧不需要探测，控制端会从后面收到的帧发现缺口；持续出帧的画面因此不会被探测，链路排队造成的反馈变慢不会引来额外的包。每帧最多探测两次，第二次等待加倍，且只在回复还赶得上截止时间时发送；探测按补传分片发送，不需要协商，旧控制端同样受益。

UDP 缺片先经过短暂乱序等待，再按剩余截止时间决定是否修复，预测帧默认最多两轮应用层补传。关键帧本身就是恢复手段：被途中队列溢出或突发丢包打掉一部分的关键帧，如果两轮后仍缺片就只能等到截止时间作废、再整幅重发，所以关键帧在截止时间内最多补传六轮，每轮只重发仍然缺少的分片，轮次间隔不小于一次往返时间。控制端支持区分补传时，会在请求中声明该能力。共享端在补发包上加标记，控制端据此将实际靠补传收到的尾片计入丢包，正常按发送节奏到达的尾片不会仅因曾被请求而计为丢包。旧端沿用原有分片格式。已经过期或无法维持参考关系的帧不无限排队等待，而是结算旧帧、切换编码代次并请求新的 IDR。普通帧与关键帧使用不同的恢复时限，关键帧的发送预算还取决于大小和当前目标速率。

TCP 媒体使用 5 秒的有限交付预算，UDP 普通帧的交付预算则按 RTT 调整。完整收到的帧另有 5 秒解码与确认预算，重复帧或重复重组确认不会续期；超过交付或确认预算会触发恢复。这些是卡死检测上限，不表示正常帧会等待 5 秒才显示。该预算通过可选本地配置只在新媒体会话启用，默认缓存行为和旧版视频协议保留。

UDP 探测每约 200 毫秒发送一次；尚未完成的挑战在一秒有效期内重复发送，避免有效 pong 因公网往返超过发送间隔而失效。挑战在首次有效回复后结算，重复或过期回复不能延长路径存活。

当前自动策略包含以下条件，它们是调度参数，不是恢复耗时保证：

能用 UDP 就用 UDP：延迟上升这类拥塞问题只降低画质，不切换路径；不伴随延迟增长的丢包由补传和前向纠错承担（见“画质上限与实际值”）；只有 UDP 连不通、失去保活，或在逐次降低画质后仍无法送达视频时，才使用 TCP。

- 初始 UDP 探测窗口约 1.5 秒（中继 5 秒）；探测不通直接使用 TCP。已使用 UDP 时，约 1 秒没有有效匹配 pong 会请求 TCP 恢复。
- UDP 上的关键帧未能送达（补传后仍缺片，或切到 UDP 后约 2 秒一帧都没解出），先把码率减半，约 1 秒后在 UDP 上重新发关键帧；连续 3 次都失败（中间没有任何一次在 UDP 上成功提交）才转入 TCP 与恢复冷却。期间旧画面保留；视频原本在 TCP 上时，重试间隙仍可在 TCP 上恢复画面，但这不算 UDP 成功，也不清零失败次数，下一次 UDP 尝试从该次恢复完成后重新计时。采集准备暂未就绪可以重试，不能当作 UDP 媒体失败。
- 网络持续恶化只交给画质调整（见“画质上限与实际值”），不再触发 TCP 试用。编解码阶段压力优先调整计算负载，不单凭计算耗时把 UDP 判为不可用。计算压力按每个约 1 秒样本窗口内编码、解码每帧耗时的平均值与帧间隔比较，超过 10% 才算；解码耗时不含排在前面帧之后的等待，单个慢关键帧或一批同时到达的帧不判为编解码跟不上。
- TCP 回退后，恢复探测按约 30、60、120、300 秒退避，后续保持在 300 秒上限。恢复探测窗口约 5 秒，需有真实媒体解码与提交，之后结合有效媒体窗口评估稳定性。UDP 从选中起持续使用约 5 分钟（暂停时间不计）后才失败的，下次退避重新从约 30 秒开始；更早失败则继续递增，避免链路每一两分钟出问题时在 UDP 与 TCP 之间每 30 秒来回切换。

单次丢包不必触发 TCP 切换。静止画面不会因为没有新帧而判为链路失败，暂停期间不累计媒体恶化时间；恢复后重新获取有效样本。系统网络路径变化会触发重新验证，具体恢复仍受路由、防火墙、DTLS/TCP 状态和新关键帧大小影响。

## 端口与仅 TCP 模式

默认被控端使用数字端口 `5908`。控制 TCP、独立视频 TCP、bulk TCP 和 UDP 使用同一个配置数字端口，不需要逐个分配新的端口号。

公网映射假设外部端口为 `Q`、被控端监听端口为 `P`：

| 路由器规则 | 目标 |
| --- | --- |
| TCP 外部 `Q` | 被控 Mac 的 TCP `P` |
| UDP 外部 `Q` | 同一台 Mac 的 UDP `P` |

例如 `Q=15908`、`P=5908`，两条规则都转发到被控 Mac 的 `5908`，控制端填写 `15908`。当前界面只有一个目标端口，无法分别填写不同的外部 TCP、UDP 端口。只开放 TCP 仍保留可用路径；UDP 被阻断时不会改用明文传输。

“画质与连接”中的“仅使用 TCP（下次连接生效）”是本机选择，修改后重新连接才生效。实际路径以会话内的“UDP 视频”“TCP 视频”或“TCP 兼容模式”为准，探测中不显示为已经使用 UDP。

应用不配置路由器、防火墙或 UPnP，不使用公共 STUN/TURN、中转服务或云账号连接；直连模式不做 NAT 穿透，端口转发仍需外部网络本身可达。配置自托管中继后，中继 UDP 视频可尝试[中继打洞](relay.md#中继打洞)。

## 画质上限与实际值

新版媒体模式从保存的画质选择或共享端配置开始，已保存设置和后续手动选择（最长边、帧率、码率）是自动调节的上限，自动调节永不超过它们。实际应用值必须经过共享端确认，界面“实际生效”以及状态栏、全屏状态中的“帧率 · 码率”显示当前值。自动降档与恢复不覆盖手动偏好，也不修改共享端默认值。

实际视频连接确认处于 Wi-Fi 或以太网的同一物理子网时，优先保持所选最长边、帧率和码率，不因编解码慢、单独丢包或解码失败降低画质。判断使用连接已解析的本地/远端地址及本机网卡掩码，不以低 RTT 或私网地址猜测；回环中继、VPN、不同子网和无法确认的路径不启用。UDP 与 TCP 均适用，切换视频路径时重新判断。

- 局域网只有视频交付延迟增长达到 80 ms、连续约 2 秒，或连续的新 RTT 测量确认至少 80 ms 延迟，才降低一档网络负载：先把码率降至约 3/4，码率不足以维持画质时再降低帧率或尺寸。RTT 证据至少需要两次新测量，间隔最多 6 秒；UDP 通常按每秒窗口累计，TCP 心跳约每 5 秒一次，单次尖峰不会重复计数。最近 RTT 偏高时，交付时间不再增长也不会被误当成已恢复，须等新的低 RTT 或路径重置。在旧版 3 帧窗口下，排队约 100 ms 时帧率上限约为 30 fps；10-24 控制端日志中滚动时延迟稳定在约 120–130 ms，低于旧的 150 ms 门槛，因此多数滚动不会触发降档。
- 因局域网延迟降档后，静止画面延迟再低也不能证明链路扛得住更高码率：改为按普通策略逐档回升，需要约 4 秒延迟低于 50 ms 且视频实际用到当前码率一半以上的样本，每次约提高 1/4；升档后约 30 秒内又因延迟降回时，下一次升档所需时长翻倍（最长约 2 分钟）。换到新的局域网路由或手动选择画质后重新开始。
- 没有发生过局域网延迟降档、只是起步较低或沿用其他路径的较低画质时，延迟低于 50 ms、连续约 3 秒有正常解码画面后，仍一次恢复到手动选择的完整上限，不等待普通策略的 5 分钟尺寸冷却。不超过用户选择或旧端能力。
- 每秒分别累计该窗口的交付延迟增长与新 RTT 证据；RTT 取最近实际 UDP 探测与本窗口收到的控制心跳测量的最大值；约每 5 秒一次的心跳只计入它到达的那一秒，不会让一次偏高的心跳连续充当几秒的延迟证据。UDP 初始估计值和过期测量不作证据；交付延迟是相对最近 30 秒最小值的增长，不是屏幕到屏幕延迟。缺测窗口不累计交付延迟或恢复时长，心跳之间允许保留 RTT 连续证据，但间隔超过 6 秒即失效；静止无视频、暂停和路径切换会清除连续计时。失败/取消的画质请求仍保留最后确认值。
- 画面恢复、重传和传输路径切换仍正常执行。保留帧率上限不意味着硬件会达到它；静止画面只做有限次数细化，不持续凑满所选帧率。

其他路径沿用以下规则。两端都支持 `adaptiveVideoV1` 时，按每秒的网络样本调整，UDP 和 TCP 规则相同：

| 样本 | 条件 | 动作 |
| --- | --- | --- |
| 严重 | 共享端测得的帧送达时间比近 30 秒最小值高出 ≥500 ms；或 UDP 丢包 ≥10% 且同时有延迟增长（送达增长 ≥80 ms 或非关键帧组装等待 ≥60 ms） | 立即把码率减半 |
| 拥塞 | 送达时间增长 ≥150 ms、非关键帧组装等待 ≥120 ms，或 UDP 丢包 ≥3% 且同时有延迟增长，持续约 2 秒 | 码率降到约 3/4 |
| 健康 | 送达增长 <80 ms、组装等待 <60 ms | 累计恢复时间 |

延迟增长是拥塞的判据，丢包和抖动本身不是：无线干扰、蜂窝或跨境链路上的丢包与发送码率无关，降低码率换不回丢失的包，只会白白牺牲画质，这类丢包由补传与前向纠错承担。

- 靠补传或纠错才收齐的帧，其组装等待和送达时间量到的是修复耗时，不计入上表的延迟证据。RTT 抖动不再单独触发降档。
- 丢包 ≥10% 持续约 2 秒而没有延迟增长时，先做一次试探：把码率降到实际接收码率的约 3/4，观察约 3 秒。链路已满时实际接收到的就是它能承载的量，留出约 1/4 给补传和校验即可，不必沿着原码率逐级减半。试探只改码率（编码器原地生效）：只要当前帧率和尺寸下还有能保持文字清晰的码率档位，就不为试探降低帧率或尺寸，避免在已经丢包的链路上重建视频流。
- 试探有三种结果。丢包降到原来的七成以下：是拥塞，保留这次降档。丢包仍在七成以上且送达流量随码率一起减少：是链路自身丢包，恢复试探前的画质，此后约 1.3 倍以内的丢包不再触发降档。丢包仍在七成以上而链路仍送达与降低前相当的流量：链路在试探档位上仍然是满的，立即按这段时间实际接收码率的约 3/4 继续降低（此时可以降低帧率和尺寸），不再重新等待。
- 这个容忍值在链路不再丢包后约一分钟内逐渐消退，更换视频路径或手动选择画质时清零。
- 升档生效后约 30 秒内丢包升到 ≥3% 且明显高于升档前（约两倍以上），视为这次升档带来的丢包，持续约 2 秒即撤回，并按下文规则延长同类升档的等待。
- 端口映射等后台传输仍在丢包 ≥3%、抖动 ≥30 ms 或延迟增长时让出带宽，不受上述容忍影响。

- 码率先调，按 1、2、3、4、5、6、8、10、12、15、20、25、30、40、50、60、80、100 Mbps 取档。只改码率时，共享端直接修改正在运行的编码器，不重建采集和编码器，也不发新关键帧。
- 码率低到每像素每帧约 0.02 bit 以下时，文字会糊，此时先把帧率降到 30 fps，再缩小最长边（不低于 1280），最后才继续降低帧率。改变帧率或最长边仍需重建并发送关键帧。
- 提高码率需要约 4 秒“健康且视频实际用到当前码率一半以上”的样本，每次约提高 1/4；静止画面不能证明链路扛得住更高码率。码率足够（每像素每帧约 0.04 bit）时，先恢复帧率，再恢复最长边，需要约 10 秒健康样本。
- 因网络降过码率后的回升另有一条更快的路：这条线路在降档前稳定生效过的码率（连续生效满 30 秒的那一档）会被记下约 10 分钟，之后只要连续约 4 秒健康且有解码画面，码率就按每次最多翻倍回到它的一半，不要求画面“用满”当前码率（安静的桌面很难用满，此前实测回到降档前一半中位约 194 秒）。超过一半之后仍按上一条逐档提高。回升途中某一步生效后约 30 秒内又因网络降回的，目标减半、等待时间翻倍；局域网路径不使用这条规则，手动选择画质或换线路时清除记录。
- 升档生效后约 30 秒内又因压力降回，视为该档暂不可持续，同类升档所需的健康时长逐次翻倍（码率最长约 2 分钟，帧率和最长边最长约 5 分钟）；升档后稳定超过约 30 秒、或手动选择画质时恢复初始等待。共享端拒绝的升档请求不计为失败。
- 链路容量未知时保守起步，再按上面的规则逐步提高：经全中继连接时从所选码率与 15 Mbps 中较低者起步；目标地址不是回环、私网、链路本地或 `.local` 等本地地址的公网直连，从所选码率与 20 Mbps 中较低者起步。局域网地址不设起步上限。同一条线路（直连按地址与端口，中继按节点与设备标识）上一次会话结束后 10 分钟内再次连接时（最常见的是断线后的自动重连），改从那次会话“稳定下来的码率”起步，窄链路不必再从默认值冲高一次，已验证过的宽链路也不必重新爬升：

- 稳定码率指在非局域网视频路径上连续生效满 30 秒的最近一档；爬升或骤降途中只停留几秒的档位不算，暂停期间不计时，会话不足 30 秒则不留记录。
- 会话结束时实际码率已低于稳定码率（正在降档中断开）说明线路可能变差了：这种记录只会把起步值压到默认值以下，不会抬到默认值以上。
- 这个记忆只在应用运行期间保存在内存里（最多 32 条线路），不写入连接记录；线路测速会话不读取也不更新它；所选画质上限仍然封顶。更换了网络但地址不变时它可能一时偏高或偏低，之后仍由上面的规则在几秒内调整。
- TCP 的丢包由系统重传，表现为送达变慢，因此 TCP 只用共享端测得的帧送达时间增长判断；旧版共享端不提供该数据，TCP 上保持原来只按计算压力调整的行为。旧版共享端也只接受原有码率档位，改码率时仍会重建编码器。

编解码跟不上与网络无关，非上述局域网路径单独调整：共享端一次只编码一帧，控制端的解码耗时从解码器能开始处理该帧时算起（不含排在同批前一帧之后的等待），两者每帧耗时中较慢的一个决定能持续的帧率（1000 ÷ 毫秒数）。约 3 秒的样本平均每帧耗时超过帧间隔 10% 以上才算跟不上，此时先把帧率直接降到能持续的档位、最长边不变（例如每帧约 10 ms 时 120 → 90 fps）；帧率最低只降到 60 fps（所选低于 60 时以所选为准）。在这个下限上仍只能持续不到约 85%（60 fps 时约 50 fps，即每帧超过约 20 ms）时，使用 HEVC 4:4:4 真彩的会话先改用 4:2:0 色度并保持画面尺寸（整幅 4:2:0 画面的文字比缩小后再放大的 4:4:4 更清楚），4:2:0 仍跟不上才缩小一档最长边；4:4:4 与尺寸一样按等待时间和实测耗时（4:2:0 的每帧耗时乘以离开 4:4:4 时测得的耗时倍数）决定何时恢复，且在尺寸回到所选之后才恢复，被控端编码器拒绝 4:4:4 时不再重试。连接记录的 `sustainedVideoSize` 同时记下是否放弃过 4:4:4（可选的 `leftTrueColor`、`trueColorCost`），界面上的“4:4:4 真彩”开关仍表示所选而非当前生效。控制端在画质高级设置里开启“清晰优先”（默认关闭，对所有连接生效，保存在本机偏好里）后，帧率下限从 60 fps 改为 30 fps：先把帧率降到编解码能持续的档位直至 30 fps，在 30 fps 上仍明显跟不上才放弃 4:4:4、再缩小尺寸；开启时会立即重试此前放弃的尺寸和 4:4:4，关闭后在下一个采样窗口把它降下的帧率恢复到 60 fps。连接记录里的 `sustainedVideoSize` 用可选的 `sharpnessFirst` 记下测得时的偏好，只供同一偏好的会话起步。接下来说的尺寸规则不变：被测出太慢的尺寸至少约 5 分钟内不再尝试；之后只有较小尺寸上实测的每帧耗时按像素数放大后仍不超过约 20 ms（即编解码确实变快了）才重试，耗时没有变化就不重试，避免每隔几分钟升上去、几秒后又降回来；这只是按像素数做的估算，为防估算偏差，距上次降回满约 1 小时后无论估算结果都会再试一次。所选帧率低于 60 fps 时没有可用于预测的耗时，只按等待时间重试。重试后没能连续出帧撑满这段等待时间就再次因编解码降回的，下次等待时间翻倍（最长约 1 小时）；撑满之后、手动选择画质或被控端换到另一种比例的显示器时重新从约 5 分钟算起。因编解码降过尺寸、且更大的尺寸之后没有撑满等待时间的，控制端把当时撑得住的最长边档位和画面比例记在这条连接记录里（可选字段 `sustainedVideoSize`，旧记录无需迁移）；下次经公网直连或中继连接同一台被控端、画面比例相同时直接从该尺寸起步，不再先用所选尺寸开流、几秒后再降一次，更大的尺寸仍按上面的等待和估算重试。局域网会话、线路测速不读取也不更新它；手动选择画质（包括重新选择同一档）会清除它并立即按所选尺寸重试。恢复更高帧率要求实测每帧耗时在新帧间隔内仍留约 15% 余量。没有耗时数据的解码失败仍先缩小最长边。诊断日志的 `streamConfigured` 对自动调整附带原因 `qualityCause`（1 网络、2 升档、3 共享端编码、4 控制端解码、5 局域网持续高延迟、6 沿用上次撑得住的尺寸起步）和计算压力时较慢一侧的每帧耗时 `computeMicroseconds`；画质提示会说明最近一次自动降档的原因。这些规则只在控制端执行，共享端照常上报编码耗时，无需新增协议字段。

能力协商：共享端在 Hello 中声明可选的 `adaptiveVideoV1`，媒体统计消息新增可选的 `deliveryMilliseconds`（只在 stats 中出现，0–60000），旧版控制端会忽略。缺少该能力时，自动调节沿用原有码率档位，且不使用细分档位。

低 RTT 不再直接把新版会话升到原分辨率 / 60 fps / 100 Mbps。旧传输继续保留原有的初次低 RTT 选档逻辑，旧端画质能力也沿用原有兼容规则。

分辨率、帧率和码率都是负载因素。帧率选项是上限，最高可选 240 fps（超过 60 fps 需双端更新），不能证明采集、编码、传输、解码和显示能持续达到该值；实际还受被控屏幕刷新率和内容变化限制。原分辨率、高码率也不能替代真实动态画面的对照测试。

## 诊断与测量边界

两端菜单栏均可开启“性能诊断”并导出本地日志。日志继续按固定窗口聚合、限制文件大小，不记录画面、按键内容、地址、配对码或媒体密钥。离线脚本可读取导出的文本：

```sh
python3 scripts/analyze-performance.py viewer.txt host.txt --output report.md
```

无论是否开启性能诊断，控制端每次把视频换到另一条路径时，常规诊断日志都会写入一条 `mediaPathSwitch`。`videoPath` 为 1 UDP、2 TCP、3 TCP 兼容模式；`switchCause` 为切换原因：1 初始期限内没有可用 UDP，2 帧恢复，3 中断后重试，4 独立视频 TCP 已关闭，10 初始 UDP 探测成功，11 冷却后恢复探测成功，14 UDP 保活约 1 秒无回应，15 UDP 上连续 3 次关键帧未能送达（之前每次在 UDP 上降低画质重试，不单独记录）；16 已提交的 UDP 视频在 10 秒内出现 3 次播放交付中断（每次都已在 UDP 上恢复过），改用 TCP。丢包率、延迟升高等网络质量本身不触发路径切换（12、13、17 为保留的策略代码）。同一路径上的帧恢复不逐条记录，次数见性能诊断中的 `mediaRecovery`。离开 UDP 的切换另带 `lossPermille`：切换前约 5 秒内 UDP 视频的丢包率（千分比），从 TCP 切回 UDP 时没有此项。

| 读数或指标 | 能说明什么 |
| --- | --- |
| 界面“丢包” / `lossPermille` | 约 5 秒内 UDP 视频分片未按时到达（超过乱序等待后需补传，或最终没到）的比例，在 UDP 试用期间也显示；整帧都没收到的不计入。只用于显示和日志，不参与切换判断。TCP 视频由系统重传，不显示 |
| 界面 RTT / `roundTrip` | TCP 控制连接的应用心跳往返，包含应用排队；5 ms 不代表操作到画面变化仅需 5 ms |
| `mediaRoundTrip` | UDP 探测的应用往返，不包含整个采集、编解码与呈现流程 |
| 控制端 FPS | 成功解码的帧数；共享端 FPS 按提交发送的帧数计算，均非物理上屏帧率 |
| `mediaReassembly` / `mediaDecodeInterval` | UDP 帧从首片到重组完成的时间，以及成功解码回调的间隔；后者也可能包含静止或帧生产间隔 |
| `mediaSwitch` / `mediaRecovery` / `mediaTransport` | 切换耗时、恢复观测与已提交路径；路径数值为 1=UDP、2=独立 TCP、3=共享 TCP |
| `mediaExpired` / `mediaRepairBytes` | 过期帧结算和应用层补传字节，不等同于网卡丢包率或 TCP 内部重传量 |
| `decodeToDisplay` / `displayEnqueue` | 最新帧等待与提交显示层的耗时；`enqueue` 完成不证明像素已出现在屏幕上 |

阶段可能重叠，不能直接相加成端到端延迟。双端单调时钟不能直接相减；日志摘要也无法还原每帧轨迹或由窗口 P95 合成全会话 P95。静止画面可能正常显示 0 fps，不能据此判断卡顿。历史阶段计时与报告解释另见 [性能诊断](performance-diagnostics.md)，新媒体指标以本文为补充。

对照时应固定同一动态内容，记录两端硬件与系统、网络、画质上限、实际生效值、路径及卡顿时间，再比较自动模式与下一次连接的仅 TCP 模式。真实操作到画面可见的延迟需要额外测量方法，不能由心跳或解码 FPS 代替。

## 验证范围与后续

已有针对性的系统 TLS/DTLS 回环、协议边界与重组、自动路径和画质策略、视频恢复 IDR、独立画布候选提交与旧回调隔离检查。它们使用本机回环、合成帧及独立检查应用，不等同于真实双机的录屏、网络和显示验收。完整检查与交付构建结果应结合对应提交及构建记录查看。

真实 M2/M3 两台 Mac 的 Wi‑Fi 动态桌面、相同内容下的自动／仅 TCP 对照、弱网与公网映射、系统网络切换、macOS 14 与 Intel 实机仍待验收。当前不承诺固定恢复秒数、持续 60 fps，或已经达到其他远程产品的实际流畅度。

新版已增加按能力协商的 [独立光标](independent-cursor.md)、分块 Reed-Solomon 多包自适应前向纠错（`blockFEC`，兼容单包 `parityFEC`）与远端系统音频（`remoteAudioV1`），旧端仍将光标放在视频中并沿用原有分片重传；系统权限要求保持原样，自托管中继及其视频打洞见[自托管中继](relay.md)。
